## Conventions

- The browser only ever calls the app's own address. Proxy route handlers at `app/v1/auth/[...path]/route.ts` and `app/transactions-api/[...path]/route.ts` forward those paths to the two services, resolving each address per request via `lib/api/serviceBaseUrl.ts` — never from a literal in application code, and never through a `next.config.ts` rewrite (a rewrite destination is resolved at `next build` and frozen into `.next/routes-manifest.json`, so the running server's configuration would be ignored). A new backend service gets its own mount folder and route handler, exporting only the verbs its spec defines and forwarding through `forwardPathToService` so the caller's path cannot leave the mount point.
- An operation whose audit identity must come from the SESSION gets its own route handler under `app/api/…` (the first is `app/api/decisions/route.ts`) instead of travelling through a `[...path]` proxy mount, which forwards caller headers verbatim and would let a browser name anyone as who did it. Such a handler resolves the identity itself with `fetchUserInfo` (`requireSession()` redirects, which is not an answer a fetch can act on), enforces the role, forwards through `forwardToService` with headers it composes itself, and passes the service's own status and body back. The proxy mount then refuses those service paths at the PATH level (404, nothing forwarded) — never by stripping the audit header globally, which would break the file cancel that legitimately sends one through it. An audit name that cannot go in a header at all (a header value is a byte string, so any code point above U+00FF — Cyrillic, CJK; accented Latin is fine) is reported as a bodyless 500 with the reason logged server-side, and the call is not sent: the name is never re-encoded, transliterated or stripped to fit, because what gets recorded as who acted is the service's contract, not the handler's to reinterpret.
- Authentication is cookie-session only: no token or credential in browser-reachable state, no auth header from the API client. Server-side calls forward the incoming `session` cookie explicitly.
- Authorisation is re-resolved per server-rendered navigation from `GET /v1/auth/userinfo`; nothing caches roles.
- Test/mock factories in `web/src/mocks/data/` re-export the production types and role constants rather than declaring their own, so mocks cannot drift from the app's contract.
- Forms compose the Shadcn `form` primitive with react-hook-form and a Zod schema from `lib/validation/schemas.ts`. Required-field checks report on blur (`mode` and `reValidateMode` both `'onBlur'`, `noValidate` on the `<form>`), server-checked rules on submit; nothing reports on a keystroke. Required fields carry an `aria-hidden` asterisk in the label plus one legend line per form.
- A failed request's message is shown to the user only when it came from the service (`serviceMessageOf`); otherwise the screen supplies its own plain wording.
- Every screen needing a session is a page under `web/src/app/(authenticated)/`. That group's layout is the only gate (`force-dynamic`, `await requireSession()`) and renders the shared header; a new protected screen adds a page there and re-gates nothing.
- An address with no screen inside the signed-in area is answered by `app/(authenticated)/not-found.tsx` — the group's own `not-found` boundary, so the group's layout (and therefore the header and its navigation) stays on the page and the user is never stranded with only the browser's Back button. Next still answers it 404. A nested segment must not add a `not-found.tsx` of its own unless it needs different wording; `notFound()` from any page in the group already lands here. An address matching no route at all lands here too, via the group's catch-all `app/(authenticated)/[...unmatched]/page.tsx`, which does nothing but call `notFound()` — so a mistyped address keeps the shell instead of falling through to Next's root fallback (which renders outside every layout). A real screen always wins over it, so adding one needs no change there; the cost is that a signed-out visitor to an unknown address is sent to sign in rather than getting a bare 404.
- The root layout renders no `<main>`. Each screen supplies its own, so the app header stays a sibling of `main` and keeps its `banner` landmark.
- Signed-in screens are FULL WIDTH and left-aligned — no width cap and no centring on the `(authenticated)` layout's `<main>`, whose screens are dense tables that a centred column would starve. The only horizontal space is padding, and the header's inner container carries the SAME padding with no cap of its own: the app's name and the content beneath it start on one vertical line, so changing either one without the other visibly misaligns the shell. A screen that needs a narrower measure constrains its own content, never the layout.
- Header/user menus are non-modal (`modal={false}`): a modal Radix menu marks the rest of the page `aria-hidden` while it stays focusable, which fails the accessibility scan.
- Authorisation for a screen lives in `lib/auth/access-map.ts` and nowhere else. An epic shipping a screen registers or edits its address there, and its page returns `<PermissionDeniedMessage deniedPath={…} />` when `canAccess(session, path)` is false, before rendering anything — no second gating mechanism, no client-side gate. An address is registered before its screen exists so a denial can never fall through to not-found.
- An address is withheld from a role only when that role may not READ the screen at all. Every registered address is open to both project roles, because §6.5 grants both of them read on what these screens show; what only one role may DO (submit a file, decide on a request) is a role check inside the screen, on that control. So the account the access map actually excludes is one whose role this project does not recognise — `hasRole` grants an unknown name nothing, and `RoleEntryPoints` / `HeaderNav` answer that case explicitly. Anything asserting exclusion (hidden-never-disabled, the in-page denial) is exercised with `userInfoWithUnrecognisedRole()` from `src/mocks/data/identity.ts`, which the Playwright auth stub can also mint a session for.
- Screens offer only what the current roles allow, as real links carrying an `href` (never a button that pushes a route), and an excluded action is left out of the markup rather than rendered disabled.
- Getting between screens is the header's job and needs no work from a new epic: `HeaderNav` offers exactly `entryPointsFor(session)` — the same facts, and the same wording, as the landing screen's entry points — so registering an address in `lib/auth/access-map.ts` is all it takes to appear in the navigation.
- Nothing in the header is hidden at any width — no collapsed menu, no CSS-hidden control, no width-branching in JavaScript. Every `a[href]`/`button` inside the `banner` has to be Tab-reachable and paint a visible focus indicator (epic 1's keyboard sweep walks all of them at desktop width), and the navigation's destinations have to be in the markup for a session's permitted set to be assertable. A header that outgrows one row wraps onto a second.
- An action that has to be agreed to before it happens goes through `components/common/ConfirmAction.tsx` — never a second dialog of its own. The caller supplies a title naming the object, what accepting does, and three phrases that do not read alike (asks / does it / backs out); the way out holds focus, nothing is sent until the confirming choice is taken, and the dialog CLOSES as the answer is given so a refusal is read on the screen behind it rather than inside a dialog the user is held in.
- Where one dialog hands straight over to another (a step that collects something, then the confirmation), the first suppresses Radix's focus restore on the way out — `onCloseAutoFocus={(event) => { event.preventDefault(); }}`, and only for that case. Radix returns focus to whatever was focused before a dialog opened, on a `setTimeout` as it unmounts, which lands AFTER the second dialog has focused its own control and pulls focus back onto the list behind both. Backing out instead of handing over must still restore normally, or the keyboard user is left on `body`.
- A control that DISAPPEARS as the result of the action it was just used for has to hand focus to a surviving control on the same object, before or as it goes. Removing a focused element drops focus to `<body>`, so a keyboard user is put back at the top of the page after every action — the same harm as disabling a control under them (see `FileDownloadActions`). The hand-off is a real one between two elements the component owns (a ref), never a search of the page for a button by its wording, and it fires on the commit that removes the control: any dialog in the flow restores focus to its own trigger on a `setTimeout` as it unmounts, so a hand-off made earlier is simply undone.
- The Shadcn `alert` default variant is the one used, with its description set to `text-foreground` and its title's one-line clamp released: the destructive variant paints the description at reduced opacity, which misses AA contrast for wording the user must act on.
- Every colour, the type face and the corner radius live in `web/src/app/globals.css` as raw-hex tokens, with a value in both `:root` (light) and `.dark`. Beyond the Shadcn set it declares `--success` / `--warning` / `--info`, `--destructive-foreground`, `--brand-accent` / `--brand-tertiary` (each with a paired foreground) and `--overlay` (the dim behind a modal), so a status, brand or modal surface never needs a Tailwind palette utility or a colour keyword. Components carry no colour value — including the CLI-generated primitives in `components/ui/`. A status is shown through the shared `StatusBadge` (see its row), which pairs the status TEXT and an icon with one of five intents — in progress or informational on `--info`, finished well on `--success`, needs attention on `--warning`, refused on `--destructive`, inert or unrecognised on `--muted` — never colour alone. A screen supplies what its own statuses MEAN, never a colour.
- Filled brand and status surfaces take the theme's own text colour as their foreground, not white: the brand blues are light, so `bg-primary text-primary-foreground` clears 4.5:1 in both themes only that way. `--input` is darker than `--border` so a field's outline clears 3:1 (WCAG 1.4.11).
- The light/dark version is expressed as the `dark` class on `<html>` and is resolved by the blocking inline script the root layout embeds in `<head>` — before first paint, never in an effect. A new screen needs no theme work; a new provider stack must not be nested around the root layout to add one.
- Browser state that already exists before React runs (the theme class, storage, a media query) is watched with `useSyncExternalStore`, never copied into React state by an effect: the lint rule `react-hooks` rejects setting state inside an effect, and a copy can disagree with what is on screen. Where the server cannot know the value, the server snapshot is the honest "not known yet" and the render handles it.
- The app's face is loaded once by `next/font` in the root layout as a CSS variable (`--font-cabin`) and reached only through the `--font-sans` token; no component names a font family.
- A choice from a fixed set is the Shadcn `select` (Radix), never a native `<select>`: the native option list is drawn by the operating system, so a keyboard-only browser test cannot focus an option, and the project's WCAG 2.2 AA keyboard-completability bar cannot be evidenced. Its trigger takes the `id` the `FormLabel` points at. Outside a form the trigger takes that `id` from its own `Label` and also `aria-labelledby` naming it: the trigger is a BUTTON, so its accessible name would otherwise be whatever value it currently displays, leaving the control unnamed for assistive technology and unaddressable by name in a test. Its option list opens with an animation and closes without one: Radix takes the whole rest of the page out of the accessibility tree while the list is open (`aria-hidden` everywhere else, its stand-in for `aria-modal`) and puts it back only when the list UNMOUNTS, so a closing animation leaves the page unreadable for as long as it plays — after the choice has been made and while the screen is already showing its answer.
- A sortable table column is a `columnheader` carrying `aria-sort` (`'none'` on every column but the one in force) with a real `button` named for the column inside it, and the direction is in that button's accessible name as well as in its arrow. A clickable `<th>` cannot be reached by keyboard at all, and an icon-only indicator leaves the state to eyesight, which R15 forbids.
- Controls that move between pages are `button`s carrying `disabled`, never anchors with `aria-disabled`: paging changes no address, `disabled` is what makes "cannot be used" programmatically determinable, and it takes the control out of the tab order so a keyboard sweep never lands on one that does nothing. Shadcn's `pagination` primitive is used for its landmark and list markup only — its own previous/next slots are `<a>`s — and its nav is labelled for what it pages rather than left as the generic "pagination", since the signed-in shell already has a navigation landmark.
- An icon-only control carries a Shadcn `tooltip` AND an `aria-label`, both built from the same string. The tooltip is what reveals the wording on hover *and* on keyboard focus; a native `title` never shows on focus, so it leaves a keyboard user with nothing. The two must match exactly — a sighted user and a screen-reader user being told different things is the defect the pairing exists to prevent. A control that has visible wording of its own needs neither. `TooltipProvider` is context only (it renders no element) and wraps whichever region holds the controls; Shadcn's `Tooltip` does not supply one. It turns Radix's hoverable content OFF, so the wording goes away the moment the pointer leaves the control: left on, Radix draws a grace area between trigger and content instead and waits for a LATER pointer move outside it, so a pointer that leaves in one movement and stops leaves the wording on screen indefinitely. A tooltip that has to be pointed INTO is the wrong primitive — that is a popover.
- Where a narrow screen needs a genuinely different presentation (not a re-flowed one), the two are branched in JavaScript on the watched media query (`lib/layout/viewport.ts`), never rendered together with one hidden by CSS. A CSS-hidden duplicate is still in the accessibility tree's reach, still doubles every value on the page for anything reading by role or by text, and still costs the render.
- Every per-request action in the expense request list is a DIRECT control on the row and on the card; there is no ⋯ action overflow menu anywhere on a request. This deliberately supersedes the MECHANISM `expense-request-list` R16 named (an action overflow at phone width) — approved by the user at manual test — while still meeting what R16 is for: every action reachable at every width, now in one activation. Do not restore the menu as a missing feature.
- A row (or card) in a list that re-renders on every keystroke is memoised on stable props — the record itself, plus one callback that TAKES the record rather than a closure built per row. That is what keeps narrowing responsive at the volume ceiling; a callback rebuilt each render silently defeats it.
- A scrollable wrapper (`overflow-x-auto`, e.g. the Shadcn `table` container) must hold keyboard-focusable content or carry `tabindex="0"` itself: axe's `scrollable-region-focusable` is tagged `wcag2a`/`wcag211`, so a wide read-only table with no control in it fails the accessibility scan.
- A choice made in one gesture — picking from a listbox, picking a file — is validated as it happens (`setValue(…, { shouldValidate: true })`), not on blur: the convention above forbids reporting on a KEYSTROKE, and a finished selection is not one. This is what lets a wrong file be refused before any request is made.
- jsdom implements no `window.matchMedia`, so `vitest.setup.ts` supplies one that matches nothing (i.e. the light theme). A test that depends on a particular media query stubs it for that test only.
- jsdom also implements no Pointer Capture API and no `scrollIntoView`, both of which Radix uses to run a listbox, so `vitest.setup.ts` supplies honest do-nothing stand-ins (guarded, reporting jsdom's true state, swallowing nothing). Any test rendering a `select` / `dropdown-menu` / `popover` needs them; without them the first click on a trigger throws.
- Playwright alert queries are scoped to a region (e.g. `getByRole('main').getByRole('alert')`): Next.js renders its route announcer as a permanently empty body-level `role="alert"`, so an unscoped query always matches two elements.
- The `(authenticated)` layout notifies the user through the root layout's `ToastProvider`, so a test rendering that layout renders it inside the provider + `ToastContainer` composition the running app always has around it.
- A message the user is given twice — once as a notification when something happens, once as text on the screen they land on — is a live region only the first time: the copy on the destination screen takes `role="note"` so a screen reader is not told the same sentence again.
- A view that keeps itself current re-reads its OWN call on an interval, only while something it shows is still in progress, and stops once nothing is — one interval at most, tied to that single fact and cleared on unmount. A re-read that fails changes nothing on screen: the last known values stay, and the failed-load state is reserved for a read that left the user with nothing (`setState(current => current.phase === 'loaded' ? current : failed)`). "Something just finished" is told from the previous status per record id, held in a ref, so a record already finished on the first read is not announced. Where a screen has SEVERAL sections that must catch up together, the one that knows whether anything is in progress owns the single interval and hands the others a changing signal prop to re-read on — never one timer per section, which would drift and multiply the load. An action whose answer says nothing about the new state (a retry) uses that same signal rather than a mechanism of its own — and, because the record may still report the state it had before the action (or already report it again), such an action ALSO keeps the interval running for a fixed number of further reads: an accepted action is itself a reason to keep asking, so the outcome cannot depend on catching an in-progress status in one sample. Bounded, so the view still goes quiet. WHERE WHAT IS BEING WATCHED IS OTHER PEOPLE'S WORK rather than a record finishing, there is no idle state to stop at, so the interval runs for as long as the view is open (the expense request list). Everything else above still holds; what replaces the stop condition is a gate on the document being visible (`lib/layout/pageVisibility.ts` — nothing is asked of a service while nobody is looking at the answer, and a reader coming back is read for straight away) plus a pause around any action of the reader's OWN that the view must not race. A read that lands then merges over what is on screen rather than replacing it (`lib/transactions/refreshing.ts`), and says what it brought on one polite live region — never a notification, a dialog or anything the reader has to dismiss.

- A section whose state is per-item — one wait, one failure, one answer per thing on offer — keys that state by the item rather than holding one shared state, whenever two of them can be in flight at once (which is the case wherever a control is deliberately left usable while its own call is out). One shared state lets whichever answers first clear or overwrite what the other reported. An in-flight guard is not the alternative: a control that looks usable must never be a silent no-op.

## Cross-epic debt

- CORS on both backends is an open backend requirement (project.md NFR-base-6). The same-origin proxy route handlers make it a non-issue for browser calls; any future direct browser-to-service call would reintroduce it.
- There is still no root `app/not-found.tsx`. Nothing inside the app reaches Next's built-in fallback any more (the signed-in group's catch-all answers unmatched addresses), so this only matters if a future public area outside that group needs its own not-found. A root boundary has no session to render a header from, so it stays separate work.
- An ad-hoc `npm run test:e2e` REUSES a dev server already listening on :3000 (`reuseExistingServer`), and one started by hand points at the real auth service rather than the run's stub — so every protected-screen spec is sent to sign-in and fails on "element(s) not found", whatever the spec was about. Stop the hand-started server, or use the epic-end form (`E2E_PROD=1`, port 3100, never reused). Nothing in the app is at fault when a whole suite fails this way.
- Against a COLD `next dev` server the sign-out specs can exceed their 5s navigation window while the proxy route handler compiles on demand; they pass on the config's one retry, and pass first time once the dev server is warm or in `E2E_PROD=1` mode. Dev-server artifact only — nothing in the app is slow in production.
- `web/src/components/ui/alert-dialog.tsx` and `dialog.tsx` (Shadcn CLI output) have their overlay changed from `bg-black/50` to the `bg-overlay/60` token; regenerating either primitive will reintroduce the colour keyword.
- The three expense-request-list tests that drive the narrowing controls — story 2's applied-summary test, both of story 3's range tests and story 4's page-controls test — can each exceed Vitest's 5s per-test timeout when the whole suite runs in parallel workers on a loaded machine (each types into several controls and re-renders the list per keystroke: ~2s in isolation, ~3x that under contention; which of them times out varies run to run). Not caused by any one story — verified on a tree with story 6 stashed, where the same three fail — and all of them pass in isolation and on a suite run that is not competing for cores. Nothing in the app is slow; if one fails a gate, re-run the file on its own rather than reshaping the component. The underlying squeeze is the template's 5s default `testTimeout` against whole-screen integration tests (logged in `template-feedback.md`).
- `web/src/components/ui/select.tsx` and `tooltip.tsx` (Shadcn CLI output) carry deliberate BEHAVIOUR edits, not just styling ones: the select's option list has no closing animation, and the tooltip provider turns hoverable content off (both explained in the file and in Conventions). Regenerating either primitive will reinstate the CLI default and, with it, a page that is briefly unreadable to a screen reader after a filter choice / a tooltip that outlives the pointer. Radix's dialog has the same aria-hidden-until-unmount behaviour behind its own closing animation; nothing observes it there, because closing a dialog returns focus and attention to the page rather than to an answer that has already changed underneath.
- `web/src/components/ui/button.tsx` and `badge.tsx` (Shadcn CLI output) hard-code `text-white` on their destructive variants. Kept as-is because white clears 4.5:1 on the destructive red in both themes, where `--destructive-foreground` would not on the `dark:bg-destructive/60` tint; regenerating either primitive will reintroduce it. No app code uses those variants.
